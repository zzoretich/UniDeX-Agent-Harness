# Security

## Reporting a vulnerability

Please do not put the details of a vulnerability in a public issue. Open an issue titled "Security contact", with no
details, and the maintainer will reply with a private way to send the report.

AgenticOS runs on your own Mac, with your own permissions: the runtime and its hooks run as you, the AgenticOS
Workbench app reads and writes your vault, and the agents it starts (Claude Code, Codex) act as you within their own
permission settings. What follows is how the app keeps what it displays from becoming what it runs.

## The app: how it is built to be safe

The Workbench shows text it did not write: notes, proposals, notifications whose stories come from the web, and agents'
output. The design treats the page that shows them as untrusted (design D7,
`docs/superpowers/specs/2026-10-05-workbench-app-design.md`; plan `docs/superpowers/plans/2026-10-05-sandbox-renderer.md`).

- **Nothing in the page can run code it was handed.** The page loads only the app's own files from `app://hud`, under a
  Content Security Policy that allows only those scripts (`script-src 'self'`, no inline script, no `eval`). Markdown is
  rendered with raw HTML off and sanitized by DOMPurify. Its two typefaces (Inter and JetBrains Mono, OFL) are copied
  into the app at build time from pinned packages, so the page fetches no fonts (`font-src 'self'`).
- **The page has no access to your Mac.** It runs in Chromium's sandbox with context isolation and no Node. Its only way
  out is `window.aos`, a short list of named functions (`app/src/preload/index.ts`). Main answers only the main window's
  own page, checks every argument against a schema, and answers each call with a result rather than an error.
- **Main decides every call** (`app/src/main/policy/`):
  - *Reads:* the vault, `~/.agents`, `~/Library/LaunchAgents`, `/etc/shells`, the app's own data, and of the Claude
    Code and Codex folders that `agenticos.json` and the environment name only what the Workbench shows:
    `agenticos.json`, skills, agents, commands and prompts. The session folders may be listed, to find out whether a
    transcript exists, but no transcript is read. Never a credential file (`auth.json`, `.credentials.json`, `.env`,
    keys), wherever it is, and never a backup of a host's config or the runtime's keys
    (`~/.local/share/unidex/backups/` and `…/keys/`, and `brain/_index/backups/` in the vault). Each of these denies is
    checked case-folded and in one Unicode form (APFS's own comparison), on the path as asked and as the disk resolves
    it at that moment, so no link, in whatever case it names its target, and no folder made after launch gets past it. Whether a program exists may be asked by its well-known
    name (`node`, `claude`, a shell) anywhere, for the pickers that look for them.
  - *Writes:* only what a Workbench surface writes (`app/src/shared/surfaces.ts`): To-Do writes `TODO.md`, Capture writes
    memories, and so on. Files and the note editor write anywhere in the vault except the runtime's folders
    (`brain/_index`, `brain/scripts`), dependency folders and every dot-path, so no page can plant a host's project
    configuration (`.claude/settings.json` hooks, `.mcp.json`, `.codex/`, `.git/hooks`). The page cannot create links or
    change a file's permissions. Spaces and Brain write no file themselves; their verbs write as their rows under
    *What the design accepts* say.
  - *Processes:* only the runtime's own commands, each with an argument rule (a background refresh, or a command of a
    surface that is on), never through a shell. The program is a bare name main finds on its own `PATH`, or an
    executable outside the vault and the app's data, which the page cannot create. The child's environment is main's,
    plus a few named variables with fixed or trusted values: never `NODE_OPTIONS`, `PATH` or `DYLD_*`, and a Claude
    or Codex folder only when it is one main trusts.
  - *Terminals:* a shell listed in `/etc/shells` (or your `$SHELL`), with no arguments. Main starts it with its own
    environment, `PATH` replaced by your login shell's (asked once, as the setup wizard does) and `CLAUDECODE` removed;
    the page still cannot set `PATH`. The Code tab starts an agent by typing its command into that shell. Spaces and
    Sessions ▸ History type a Resume line only with a lowercase UUID from the scan (History's also the one in its
    transcript's file name) and, for Codex, `-C <folder>`, the folder the scan recorded, quoted; a line whose model, id
    or folder starts with `-` or holds a control character (C0 or DEL, such as ^U, which would act on the shell's line)
    is refused, not typed. A Clone line is typed only for a URL matching the GitHub rule (a
    `https://github.com/<owner>/<repo>` URL or GitHub's SSH form of it, quoted).
  - *Appearance:* the page may set the theme to `system`, `light` or `dark` and nothing else; main saves the choice in
    the app's data (`app-settings.json`), never in the vault, and hands it to macOS's `nativeTheme`.
  - *Setup (phase 5; install-import B1, B2, B13, B14):* the wizard names a fix by id; what it does is main's
    (`app/src/main/policy/setup.ts`). A missing tool is a download (`app/src/main/setup/toolchain.ts`) from the pins the
    app carries (`toolchain-manifest.json`: for Node, uv, Ollama, Claude Code and Codex, an https URL, a size and a
    SHA-256 per Mac arch, and the Developer ID team that signs it). The download goes through Electron's `net` (the
    system's proxy and certificates) into the app's data folder; it is hashed as it arrives, more bytes than pinned stop
    it, and a size or hash that differs deletes it and fails the fix. Only a matching file is unpacked (`/usr/bin/tar`,
    `/usr/bin/ditto`), into a staging folder; every executable it installs (Node's `node`; uv's `uv` and `uvx`;
    Codex's `codex`, `codex-code-mode-host` and `rg`; Claude Code's binary) is checked again with
    `codesign --verify --strict` and its team, and the Ollama app with `--deep` and Gatekeeper (`spctl -a`), before
    anything is moved into place. It goes only where each tool's own installer puts it: Node into
    `~/.local/share/unidex/node` (a version folder and a `current` link), uv into `~/.local/share/unidex/uv/<version>`
    linked from `~/.local/bin`, the Ollama app into `/Applications` (else `~/Applications`), opened hidden, and never
    over an Ollama that is there; Claude Code runs its own checked binary's `claude install`; Codex is laid out as its
    own installer lays it out (`<codex home>/packages/standalone`, linked from `~/.local/bin`). Anything already at a
    destination that is not a link into the installer's own tree (another uv, an npm codex, a half-installed release)
    is moved aside to `<name>.unidex-backup-<time>` and logged, never replaced unseen; this job deletes only its own
    staging. A release already there (Node, uv, Codex) is reused only when every executable in it passes the same
    signature and team check, before anything in it runs; otherwise it is moved aside and the checked download installed.
    An Ollama app already there is opened only after `codesign --deep`, its team, Gatekeeper and the version floor
    pass; otherwise it is left unopened and the wizard says how to repair or update it. The uv the checks validated is
    the one `aos init` installs graphify with (`AOS_UV_BIN`). A job that is stopped stops after
    the program it was running, moves nothing more and ends as stopped. Ollama's models come through its own API on
    127.0.0.1. Nothing needs Homebrew or npm, and nothing runs through a shell but the two
    logins (`claude auth login`, `codex login`), fixed commands run by `/bin/sh -c` in a terminal the wizard shows. A
    development run (never a packaged one) may read another manifest from `$AOS_TOOLCHAIN_MANIFEST`, which may name
    127.0.0.1 and no team: the end-to-end suite's stand-ins. `aos init` and `aos upgrade` are the bundled runtime's CLI,
    run with the `node` main found, never through a shell and with no stdin; `--host none` installs with no host, and a
    `--host` that would turn off a wired host is refused. Background model calls go only to a host the user enabled
    (or the one `provider` names). The
    persona answers are checked against the interview's rules, written to the app's data folder (mode 0600) and
    removed when `aos init` ends. The `CLAUDE.md` line and file, and Finish's PATH line
    (`export PATH="$HOME/.local/bin:$PATH"`, into `~/.zprofile`, `$ZDOTDIR`'s when set), are main's to compute; a file that
    exists but cannot be read is refused with the reason, never replaced, and a link (even to a file not there yet)
    stays a link, its target written; each line is appended once, only when the page asks (a Claude Code install; the PATH box ticked, after the install and before a
    vault is attached). Install runs only with no vault attached, upgrade only when the app's runtime is newer than the
    vault's, and one job runs at a time, the import scan included (a second ask while it runs gets the same answer; no
    other step starts until it ends; Stop, the page going away and quitting kill it, as they stop any job). "Bring in
    your history" (B9, B13; `setup:import-scan`, `setup:import`) runs only after this wizard's install and before a
    vault is attached: main runs the bundled CLI's `aos import --dry-run --json` (it writes nothing; stopped after 3
    minutes) and hands the report to the page, then `aos import` with the hosts (`claude`, `codex`) and kinds the page
    ticked and only those workspace proposals the scan listed (any other id is dropped); the argv is the one
    `obsidian-plugin/src/data/importModel.ts` builds and the `import` surface admits. An earlier install's host that
    the user's choice would drop (inspection F7: `aos init` refuses such an install, never unwiring a host) is taken
    out only on the page's ask, before the install, with the bundled CLI's `aos uninstall --host <claude|codex>`
    (`setup:unwire`), and main checks the premise itself: that host is on in `agenticos.json`, the vault that file
    names is not there (else it is an install in use, on a disk not connected or set up meanwhile, and is refused), and
    the host choice the page sends with it drops that host (a choice that keeps it is refused).
  - *The OS:* links open in the browser over https only. A document or a folder opens with its app; a file that would
    run when opened (a script, a `.terminal` or `.command` file, an app or other bundle), or a web page anywhere but the
    runtime's own proposal pages, is shown in Finder instead. A folder is never deleted for good: it goes to the
    Trash, and the runtime's folders (`brain/_index`, `brain/scripts`) are never moved, trashed or removed.
- **Packaged builds cannot be driven from outside.** The fuses turn off `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` and
  `--inspect`, and the archive is integrity-checked. Chromium's remote debugging has no fuse, so a release build refuses
  to start with `--remote-debugging-*`, `--inspect*` or `--js-flags` (`app/src/main/policy/debug.ts`;
  `npm run dist:verify` checks it). Releases are signed with a Developer ID under the hardened runtime and notarized.
- **Updates come only from this repo's releases, signed like the app.** electron-updater reads `latest-mac.yml` from the
  latest GitHub release and downloads the zip it names over https, checking its sha512; Squirrel.Mac then installs it
  only if its code signature satisfies the running app's designated requirement (same Developer ID team). A dev run
  and the smoke build never update; `updates.check: false` turns updates off.

## What the design accepts

| Risk | Why it stays | What limits it |
|---|---|---|
| The Code tab is a shell | It is the feature: what you type runs as you. A compromised page could type into a terminal it opens | Nothing in the page can run code (CSP, sanitized Markdown, no remote content), so a page must first be compromised; the terminal starts only a listed shell |
| The page can do what the Workbench's buttons do | Routines run agent prompts, Settings changes settings, Agent Teams approves gates | Each is a named command with an argument rule; nothing outside the surfaces runs |
| The page can make the Chief of Staff write a briefing now | Pulse's ↻ (spec 2026-10-08-pulse-cockpit-design P13) | One rule on the Pulse surface: `persona/briefing.js --force` and nothing else. It makes one model call through `provider.js`, under the daily duty cap (`persona.perDayUsd`), and writes only `brain/_index/briefing.json`; nothing runs while the persona is off |
| The page can create, move and rename workspaces and set workspace.md fields | Spaces' New, Adopt, Archive, Restore, Rename, Pin and Set status (spec 2026-10-09-spaces-redesign D15–D18) | Named `aos workspace` verbs, each with an argument rule; the runtime checks every name and path, writes only `workspaces/**` and `brain/_index/**` plus a project note's status tag, moves folders only between `workspaces/` and `workspaces/_archive/`, deletes nothing, follows no symlink, refuses a linked `workspaces/`, `workspaces/_archive`, map, thread or project-note folder (each must be a plain folder inside the vault), never writes a map over another, matches a name to its folder exactly, refuses headless runs, and asks before every move. On by default since 1.7.0, after a live check on each host |
| The page can mark memories reviewed, pin them, change their status or title, archive, restore and supersede them, merge memories into one and undo a merge, dismiss the sweep's suggestions, approve or reject feedback drafts, fix what Health's hygiene check finds, and preview recall | The Brain tab's Review, Library, Bootstrap, Map and Health (spec 2026-10-11-brain-hub D3–D7, D13, D14, D17, D18, D20–D22; 2026-10-12-brain-hub-ai A1, A2, A9, A10, A13) | Named `aos memory` verbs on the `brain` surface, each with an argument rule: a memory path is `brain/memory/<user\|feedback\|projects\|reference>/<slug>.md` (no sub-folder, no `..`, no dash first), 1 to 50 per call, `--json` last; `set` is compare-and-set on the hash the page read (`--expect`) and takes only `pin`, `status` (active, complete, paused), a one-line `description` (no `](`) or a one-line `title` (at most 120 characters, no control characters, no `[` or `]`, so a memory's `MEMORY.md` line never links another path: it rewrites the memory's heading and its `MEMORY.md` line, never the file name), and `--skip-brain-md` (Bootstrap's bulk Mark complete then runs `build-brain-md.js`, with no argument, once); a draft is a plain slug; `fix` takes one kind (`sources`, `types`, `descriptions`, `index`, `drafts`) and nothing else but `--dry-run` or `--expect` with a dry run's 32-character hash; `merge` takes 2 to 6 different memories, `--into` with one JSON object and `--expect` with exactly one hash per memory, comma-joined in the same order; `unmerge` one memory and `--expect` its hash; `sweep dismiss` a suggestion's 12-character hex id (`merge-draft` and `sweep` are the next row's). A merge (`lib/memory-merge.js`) refuses, writing nothing, when any memory is archived, superseded, without frontmatter or changed since its hash, and when a field does not fit (an empty field, a line break or other control character in the title or description, a `[` or `]` in the title or a `](` in the description, a title over 120 characters, a description over 200, a body over 16,000: refused, never cut or cleaned); it writes the description quoted when YAML needs it and the title as the body's heading, and drops a leading `---` block or heading from the body. Under `MEMORY.md`'s lock it first writes a record to `brain/_index/memory-merges/` (a plain folder, atomically) holding what the merge changes as it was before: the oldest memory's text and `MEMORY.md` line, every other memory's text, and `MEMORY.md`'s text (left out, so Undo puts lines back instead, only when the record would pass 16 MiB; past that even without it, the merge is refused), with the hash each file has after; then it writes the merged text over the oldest, which keeps its path, links and pins (`reviewed: true`; `pin: true` when any memory was pinned), supersedes the others in place as `supersede` does, and replaces their `MEMORY.md` lines with the oldest's. `unmerge` runs only while the merged memory's hash is the one the merge wrote: it puts the oldest's text back, each other memory still as the merge left it back byte for byte (one changed since that still says it was superseded by the oldest gets its status back as `restore` does; any other is left alone), and `MEMORY.md` back byte for byte when it is as the merge left it and every other memory came back, else line by line (a change made since elsewhere in it stays). The runtime (`lib/memory-ops.js`) checks each path again, opens it as a regular file (`O_NOFOLLOW`) inside plain vault folders, rewrites only its own frontmatter lines, `MEMORY.md`, the trail and `brain/_index/**` (BRAIN.md through `build-brain-md.js`), atomically and under locks. A hygiene fix (`lib/memory-fix.js`) re-reads the files and changes only live memories (never archived or superseded ones), keeping every other byte: `sources` their `source:` line (`session`, `in-session` or `wrap` becomes `manual-wrap`); `types` their `type:` line (`type: memory`) and `tags:` line (the `memory/<type>` tag; no status is added); `descriptions` a new `description:` line copied from the memory's own `MEMORY.md` line (one line, control characters out, at most 200 characters, quoted when YAML needs it: double quotes, else single quotes with `'` doubled, so strict YAML reads the same text); `index` `MEMORY.md` lines, under its lock (a missing line added under its type's heading, a misfiled line moved unchanged, and a line removed only when nothing at all is at its path, when its memory is archived or superseded, or when it is a second copy of a line its memory keeps, each removal named with its reason; a linked `MEMORY.md` is refused); `drafts` removes an approved feedback draft left behind, one with the slug and the title of a live feedback memory (a regular file read `O_NOFOLLOW` in a plain folder; a new rule that only shares the slug is kept). The page runs each fix with `--dry-run` first, which writes nothing (no file, no trail row), lists every change with the changes' hash, and asks in a confirm; the real run gets that hash (`--expect`) and refuses, writing nothing, unless the files still give exactly the changes listed. It logs a `fixed` trail row per changed memory or draft, and one per memory whose `MEMORY.md` lines it removes, naming each field's before and after (Restore does not undo a fix). Nothing is deleted but a feedback draft that is approved (it moves into the store) or rejected (as `feedback-review` does today), an approved draft's leftover file (`fix drafts`), and a merge record older than 30 days (`brain-hub.js` removes it at its next build: a regular file in a plain folder, nothing else there); archiving and superseding tag a memory in place and Restore undoes both. Archive of more than one memory, a draft's Reject, "Mark everything before", Bootstrap's "Mark the N complete", every fix, Undo merge, a sweep card's Archive and Retitle, and Consolidate with AI ask first; a merge is saved only from the dialog that shows its text. Bootstrap's recall preview runs `sdk/recall-cli.js <query> --limit N --json`: the typed text as one argument that is never a flag (no leading dash, so never `--warm`), with no control or line-separator characters and at most 200 characters, and a one- or two-digit limit. It reads the recall index and writes nothing but a missing one (rebuilt as `aos recall --warm` would: `brain/_index/recall-index.json` and `recall-wake.md`), logs no usage (D9), and calls no model, except that with an embed index it asks the local Ollama (the configured address, under the `auto` or `ollama` provider, or the local engine's embedder at `local.url` under `local`) to embed the query: it never resolves the provider, so it writes no `provider-state.json` and runs no headless login probe, and with Ollama down the hits are BM25's. `brain-hub.js` (the hub's caches, `brain/_index/brain-hub.json` and `brain-map.json` only, the map read from graphify's `graph.json`, and the merge records' 30-day prune) runs after an action, from Health's Rescan, and when the tab is shown with memories the cache does not hold yet. Pulse no longer writes memory: its trail keep, edit and revert (revert deleted the file) gave way to these verbs. On by default, after a live check on each host's memories |
