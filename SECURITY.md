# Security

## Reporting a vulnerability

Please do not put the details of a vulnerability in a public issue. Open an issue titled "Security contact", with no
details, and the maintainer will reply with a private way to send the report.

AgenticOS runs on your own Mac, with your own permissions: the runtime and its hooks run as you, the AgenticOS
Workbench app reads and writes your vault, and the agents it starts (Claude Code, Codex) act as you within their own
permission settings. What follows is how the app keeps what it displays from becoming what it runs.

## Superpowers integration

The setup wizard can install the official third-party Superpowers plugin into selected Claude Code and Codex host profiles. It is a separate host plugin fetched from the host marketplace; UniDeX does not bundle its code, run it in background duties, or uninstall it. The Settings surface can run only the fixed `aos superpowers install` follow-up after the user enables the preference. The optional upstream visual companion can load a remote logo if a user later activates it; UniDeX does not activate that feature or send integration telemetry.

## The app: how it is built to be safe

The Workbench shows text it did not write: notes, proposals, notifications whose stories come from the web, and agents'
output. The design treats the page that shows them as untrusted (design D7,
`docs/design/specs/2026-10-05-workbench-app-design.md`; plan `docs/design/plans/2026-10-05-sandbox-renderer.md`).

- **Nothing in the page can run code it was handed.** The page loads only the app's own files from `app://hud`, under a
  Content Security Policy that allows only those scripts (`script-src 'self'`, no inline script, no `eval`). Markdown is
  rendered with raw HTML off and sanitized by DOMPurify. Its two typefaces (Inter and JetBrains Mono, OFL) are copied
  into the app at build time from pinned packages, so the page fetches no fonts (`font-src 'self'`).
- **The page has no access to your Mac.** It runs in Chromium's sandbox with context isolation and no Node. Its only way
  out is `window.aos`, a short list of named functions (`app/src/preload/index.ts`). Main answers only the main window's
  own page, checks every argument against a schema, and answers each call with a result rather than an error.
- **Main decides every call** (`app/src/main/policy/`):
  - *Reads:* the vault, `~/.agents`, `~/Library/LaunchAgents`, `/etc/shells`, the app's own data, and of the Claude
    Code and Codex folders that `agenticos.json` and the environment name only what the Workbench shows:
    `agenticos.json`, skills, agents, commands and prompts. The session folders may be listed, to find out whether a
    transcript exists, but no transcript is read. Never a credential file (`auth.json`, `.credentials.json`, `.env`,
    keys), wherever it is, and never a backup of a host's config or the runtime's keys
    (`~/.local/share/unidex/backups/` and `…/keys/`, and `brain/_index/backups/` in the vault). Each of these denies is
    checked case-folded and in one Unicode form (APFS's own comparison), on the path as asked and as the disk resolves
    it at that moment, and a denied folder also by its identity (device and inode), so no link, in whatever case or
    under whatever other name for the folder it names its target, and no folder made after launch gets past it.
    Whether a program exists may be asked by its well-known name (`node`, `claude`, a shell) anywhere, for the pickers
    that look for them.
  - *Writes:* only what a Workbench surface writes (`app/src/shared/surfaces.ts`): To-Do writes `TODO.md`, Capture writes
    memories, and so on. Files and the note editor write anywhere in the vault except the runtime's folders
    (`brain/_index`, `brain/scripts`), dependency folders and every dot-path, so no page can plant a host's project
    configuration (`.claude/settings.json` hooks, `.mcp.json`, `.codex/`, `.git/hooks`). Paths are compared the way the
    disk compares them (any case, any Unicode form) and checked both as written and where the disk resolves them, so no
    spelling, no link and no other name for the vault's folder reaches those folders. The page cannot create links or
    change a file's permissions, and nothing it writes or copies becomes executable: a new file never is, and a file
    that was there keeps its own mode (a script of yours stays as you set it). A file with other names on disk (a hard
    link, which no path check can follow to its other names) is never changed or removed by the page; renaming or
    moving it changes no contents and stays allowed. A move to the Trash is checked and done with no other change of
    the page's in between. Spaces and Brain write no file themselves; their verbs write as their rows under *What the
    design accepts* say.
  - *Processes:* only the runtime's own commands, each with an argument rule (a background refresh, or a command of a
    surface that is on), never through a shell. The program is a bare name main finds on its own `PATH`, or an
    executable outside the vault and the app's data (under any name for those folders), which the page cannot create.
    The child's environment is main's, plus a few named variables with fixed or trusted values: never `NODE_OPTIONS`,
    `PATH` or `DYLD_*`, and a Claude or Codex folder only when it is one main trusts.
  - *Terminals:* a shell listed in `/etc/shells` (or your `$SHELL`), with no arguments. Main starts it with its own
    environment, `PATH` replaced by your login shell's (asked once, as the setup wizard does), and without the markers a
    Claude Code or Codex session that launched the app leaves in it (`CLAUDECODE`, every `CLAUDE_CODE_*` and
    `CLAUDE_AGENT_SDK_*`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CODEX_SANDBOX`, `CODEX_SANDBOX_NETWORK_DISABLED`,
    `CODEX_THREAD_ID`, `CODEX_SESSION_ID`; code-chat R64). A `CLAUDE_CODE_*` setting given to the app's environment with
    `launchctl setenv` (or a launchd plist) goes with them (code-chat R74): set it in Claude Code's settings (`env`) or
    a shell startup file instead, which still reach the agent. The page still cannot set `PATH`. While the `computer`
    surface is on, the Code tab starts an agent as the terminal's own process instead (agent-computer D18; *The Computer
    pane* below): the binary the runtime resolves on that `PATH`, whose install form main checks, with only the words
    `launchArgs` emits after it (`policy/agent-launch.ts`), in a folder a shell could start in, and with the environment
    your `$SHELL` gives a typed command (main runs it as a login, interactive shell for each launch and reads its
    exports, so your profile and rc files' variables reach the agent as they did a typed line; the shell starts without
    those markers, and `CLAUDECODE` still goes). With the surface off main checks nothing and the page types the line
    into a shell, as before the computer; when main cannot vouch for the binary, or the shell gives no environment (a
    startup file that exits, hangs or execs something else), it says why and the page does the same. Spaces and Sessions
    ▸ History type a Resume line only with a lowercase UUID from the scan (History's also the one in its transcript's
    file name) and, for Codex, `-C <folder>`, the folder the scan recorded, quoted; a line whose model, id or folder
    starts with `-` or holds a control character (C0 or DEL, such as ^U, which would act on the shell's line) is
    refused, not typed. A Clone line is typed only for a URL matching the GitHub rule (a
    `https://github.com/<owner>/<repo>` URL or GitHub's SSH form of it, quoted).
  - *Code's Diff (code-chat C8):* read-only git in a vault workspace or the code folder linked to one, chosen in main from
    the terminal's own starting folder (`code:git` names a terminal, never a folder). It needs no write surface; it refuses
    the vault root, home and the hosts' config folders, and any folder that is neither a workspace nor a linked one.
  - *Code's images (code-chat C7; the `code` surface):* The Code composer can save a pasted image (PNG, JPEG, GIF,
    WebP ≤ 10 MB, checked by content) into the app's own data folder; the page never names the path. Images are kept
    about three months, and the folder holds at most 2 GiB or 5,000 files (R59).
  - *Appearance:* the page may set the theme to `system`, `light` or `dark` and nothing else; main saves the choice in
    the app's data (`app-settings.json`), never in the vault, and hands it to macOS's `nativeTheme`.
  - *Setup (phase 5; install-import B1, B2, B13, B14):* the wizard names a fix by id; what it does is main's
    (`app/src/main/policy/setup.ts`). A missing tool is a download (`app/src/main/setup/toolchain.ts`) from the pins the
    app carries (`toolchain-manifest.json`: for Node, uv, Ollama, Claude Code and Codex, an https URL, a size and a
    SHA-256 per Mac arch, and the Developer ID team that signs it). The download goes through Electron's `net` (the
    system's proxy and certificates) into the app's data folder; it is hashed as it arrives, more bytes than pinned stop
    it, and a size or hash that differs deletes it and fails the fix. Only a matching file is unpacked (`/usr/bin/tar`,
    `/usr/bin/ditto`), into a staging folder; every executable it installs (Node's `node`; uv's `uv` and `uvx`;
    Codex's `codex`, `codex-code-mode-host` and `rg`; Claude Code's binary) is checked again with
    `codesign --verify --strict` and its team, and the Ollama app with `--deep` and Gatekeeper (`spctl -a`), before
    anything is moved into place. It goes only where each tool's own installer puts it: Node into
    `~/.local/share/unidex/node` (a version folder and a `current` link), uv into `~/.local/share/unidex/uv/<version>`
    linked from `~/.local/bin`, the Ollama app into `/Applications` (else `~/Applications`), opened hidden, and never
    over an Ollama that is there; Claude Code runs its own checked binary's `claude install`; Codex is laid out as its
    own installer lays it out (`<codex home>/packages/standalone`, linked from `~/.local/bin`). Anything already at a
    destination that is not a link into the installer's own tree (another uv, an npm codex, a half-installed release)
    is moved aside to `<name>.unidex-backup-<time>` and logged, never replaced unseen; this job deletes only its own
    staging. A release already there (Node, uv, Codex) is reused only when every executable in it passes the same
    signature and team check, before anything in it runs; otherwise it is moved aside and the checked download installed.
    An Ollama app already there is opened only after `codesign --deep`, its team, Gatekeeper and the version floor
    pass; otherwise it is left unopened and the wizard says how to repair or update it. The uv the checks validated is
    the one `aos init` installs graphify with (`AOS_UV_BIN`). A job that is stopped stops after
    the program it was running, moves nothing more and ends as stopped. Ollama's models come through its own API on
    127.0.0.1. Nothing needs Homebrew or npm, and nothing runs through a shell but the two
    logins (`claude auth login`, `codex login`), fixed commands run by `/bin/sh -c` in a terminal the wizard shows. A
    development run (never a packaged one) may read another manifest from `$AOS_TOOLCHAIN_MANIFEST`, which may name
    127.0.0.1 and no team: the end-to-end suite's stand-ins. `aos init` and `aos upgrade` are the bundled runtime's CLI,
    run with the `node` main found, never through a shell and with no stdin; `--host none` installs with no host, and a
    `--host` that would turn off a wired host is refused. Background model calls go only to a host the user enabled
    (or the one `provider` names). The
    persona answers are checked against the interview's rules, written to the app's data folder (mode 0600) and
    removed when `aos init` ends. The `CLAUDE.md` line and file, and Finish's PATH line
    (`export PATH="$HOME/.local/bin:$PATH"`, into `~/.zprofile`, `$ZDOTDIR`'s when set), are main's to compute; a file that
    exists but cannot be read is refused with the reason, never replaced, and a link (even to a file not there yet)
    stays a link, its target written; each line is appended once, only when the page asks (a Claude Code install; the PATH box ticked, after the install and before a
    vault is attached). Install runs only with no vault attached, upgrade only when the app's runtime is newer than the
    vault's, and one job runs at a time, the import scan included (a second ask while it runs gets the same answer; no
    other step starts until it ends; Stop, the page going away and quitting kill it, as they stop any job). "Bring in
    your history" (B9, B13; `setup:import-scan`, `setup:import`) runs only after this wizard's install and before a
    vault is attached: main runs the bundled CLI's `aos import --dry-run --json` (it writes nothing; stopped after 3
    minutes) and hands the report to the page, then `aos import` with the hosts (`claude`, `codex`) and kinds the page
    ticked and only those workspace proposals the scan listed (any other id is dropped); the argv is the one
    `hud/src/data/importModel.ts` builds and the `import` surface admits. An earlier install's host that
    the user's choice would drop (inspection F7: `aos init` refuses such an install, never unwiring a host) is taken
    out only on the page's ask, before the install, with the bundled CLI's `aos uninstall --host <claude|codex>`
    (`setup:unwire`), and main checks the premise itself: that host is on in `agenticos.json`, the vault that file
    names is not there (else it is an install in use, on a disk not connected or set up meanwhile, and is refused), and
    the host choice the page sends with it drops that host (a choice that keeps it is refused).
  - *The OS:* links open in the browser over https only. A document or a folder opens with its app; a file that would
    run when opened (a script, a `.terminal` or `.command` file, an app or other bundle), or a web page anywhere but the
    runtime's own proposal pages, is shown in Finder instead. A folder is never deleted for good: it goes to the
    Trash, and the runtime's folders (`brain/_index`, `brain/scripts`) are never moved, trashed or removed.
- **Packaged builds cannot be driven from outside.** The fuses turn off `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` and
  `--inspect`, and the archive is integrity-checked. Chromium's remote debugging has no fuse, so a release build refuses
  to start with `--remote-debugging-*`, `--inspect*` or `--js-flags` (`app/src/main/policy/debug.ts`;
  `npm run dist:verify` checks it). Releases are signed with a Developer ID under the hardened runtime and notarized.
- **Updates come only from this repo's releases, signed like the app.** electron-updater reads `latest-mac.yml` from the
  latest GitHub release and downloads the zip it names over https, checking its sha512; Squirrel.Mac then installs it
  only if its code signature satisfies the running app's designated requirement (same Developer ID team). A dev run
  and the smoke build never update; `updates.check: false` turns updates off.

## The Computer pane

Release 1 of the agent computer (`docs/design/specs/2026-11-06-agent-computer-design.md`) is a browser in the app that a
session's agent drives through thirteen `computer_*` tools in the agenticos MCP server and the person watches, answers and
takes over in a pane on the Code and Sessions pages. It runs only while its `computer` surface is on
(`app/src/shared/surfaces.ts`): on by default since its live check on each host (2026-11-08), and with it off (a run whose
`AOS_APP_WRITE` leaves it out) main
starts no bridge, answers the pane's calls with a refusal and records `computer: "off"` in the vault marker, so the tools
say the pane is off; with it on but no bridge started (no peer addon, no socket path, a failed listen) the marker says
`computer: "failed"` and the tools say that instead. The marker also holds main's pid, and at quit it loses its Computer
state, so after a quit or a crash the tools say the app is not running. `computer.enabled` in Settings switches it off
inside the surface.

- **The view is its own locked-down browser** (`app/src/main/computer/browser.ts`). Each tab is a `WebContentsView` in
  the shared `persist:computer` partition (the person signs in once and it remembers, D9), with Chromium's sandbox,
  context isolation and no preload: nothing of the app's bridge reaches a page. Navigation allows only `http:` and
  `https:` (and an empty `about:blank`) for the agent's opens, redirects, a page's own navigations and new windows;
  `javascript:`, `data:`, `blob:`, `file:`, the app's own schemes and browser-internal pages are refused, and an
  external app's scheme is never opened. The view's start page is DuckDuckGo (`hud/src/data/computerStart.ts`): a new
  tab the person opens with the pane's **+** loads `https://duckduckgo.com/`, and words typed in the address bar that are
  not an address (spaces, one word with no dot, a question) are sent to DuckDuckGo as a search,
  `https://duckduckgo.com/?q=<the words>`; an address or a URL opens as typed. A tab an agent opens loads the agent's
  URL with no DuckDuckGo load first, and the agent's tool description points it at the same search. These are ordinary
  page loads in the shared partition (DuckDuckGo's cookies and settings stay there like any site's) under the same http
  and https rule; nothing in the gate changes for them. Every permission is denied unless the person allows it on an
  ask card, and the camera, the microphone and the location are denied without one (the app has no access to them on
  the Mac, so an Allow would do nothing), with a line in the activity log saying so.
  Downloads and file choosers always ask; a file chooser gives a file only to the tab that asked, still on the same page
  after the Allow and after the system dialog closes; a download's bytes go to a private folder of their own (0700) in the user's
  system temp folder and move into Downloads only after Allow, never over a file (Chromium may have the whole file
  before anyone answers); Deny deletes them, and so does the browser going or the app quitting, and a folder a crash
  left behind is swept at the next start. A page's own dialogs are off in these tabs (`alert`, `confirm`, `prompt`; `confirm()` answers false):
  a native dialog from a tab parked off-screen would sit on the desktop, where a page could also use it to look like
  the app. Main drives the views through each one's own `webContents.debugger` (the DevTools protocol in process): no
  debugging port is opened and the HUD page is never attached. Page text that reaches the model is wrapped as untrusted
  data with its origin, and a navigation a page starts on its own is noted in the computer's activity log and the agent's
  Chat thread (D21).
- **The pane's own navigation buttons are the person's.** `computer.nav` moves the selected browser's active tab back or forward in its own history, or reloads it; it takes one of three words and no address. Nothing asks, as for the address bar, and the page it reaches is held by the gate like any other.
- **The page switches one session's browser on or off.** `computer.power` turns one session's browser on or off; the key must be a terminal or a thread the app holds.
- **The page names Code sessions and hands a browser on.** `computer.describe` names a Code session for the app's own cards; the title is stripped of control and direction characters and cut at 60. `computer.move` hands one Code terminal's browser to the terminal that replaces it; both must be terminals the app holds. `<user data>/computer/browsers.json` (mode 0600) keeps each browser's power and tab addresses.
- `computer.openLink` opens a web link clicked in a session in that session's browser (session-browser S14; `hud/src/data/linkRoute.ts`): http and https only, no credentials in the address; the key must be a terminal or a thread the app holds. Outside a session nothing changes: https goes to the default browser and http opens nowhere.
- `computer.openOutside` sends the selected browser's active tab to the Mac's own browser (session-browser S24, the pane's Open in my browser): it takes no argument, so the page cannot name an address; main reads the active tab's real address from the browser (an awake one only; an asleep or off browser, or a tab with no address, answers `ENOENT`), decides for itself that it is `https:` (anything else answers `EROFS` and goes no further, so no refused address reaches the log), and only then hands it to the app's external-open path and waits for the system to take it (`openExternalAwaited`; links keep the fire-and-forget `openExternalSafe`). When the system does not take the page it answers `EIO` ("Your browser did not open the page.") and writes no line saying it opened. The tab stays open either way, and the activity-log line names no address.
- The browser also listens to a tab's console messages and to its Network protocol events for `computer_console`, and keeps a load method per history entry; it keeps no header and no body, and what it prints is scrubbed like page text. The protocol's Runtime domain is not enabled, so a page cannot tell from it that the browser is driven.
- **What `computer_console` can show an agent.** The errors, warnings, uncaught exceptions and failed requests of the tab its `tab` argument names (the active one by default) since it loaded. Console messages are kept from the main frame and from any frame in the main frame's process tree; requests are kept from the main frame and from the same-site frames the browser has read from the page (it reads them after every load and as the page changes, with no snapshot needed), so a request made before that first read, and any request from a frame of another site, is dropped. Entries from frames of another site are dropped unread, since nothing scrubs values the app cannot read. What is kept is cleaned (addresses made plain and scrubbed like page text, the text wrapped as page text): the newest 200 entries, of at most 2,000 characters each, and the app takes in at most 100 messages and requests a second.
- **Password values never reach the agent** (D9). A field is sensitive once it was ever `type=password` or carried a
  password or one-time-code `autocomplete`, and stays so after a Show password reveal. Snapshots print `••••••` for its
  value and drop it from every other line; screenshots are painted over its box before the image leaves main; typing
  into one is refused, and so is any key into one but Return (which asks) and the navigation keys. A frame from another
  site cannot be read through the view's debugger session, so it fails closed: its box is painted over in screenshots,
  input into it asks on every site, and typing into it is refused. To scrub values from text a tab shows later (a URL
  a form submitted, a page that echoes one), each tab remembers the sensitive values it read, by site, in the main
  process's memory for the tab's life, never on disk: up to 256 values, or 2,048 when a site's most recent one-time codes
  and passwords are all kept.
- **Only an agent the app itself started is admitted** (D18; `bridge.ts`, `admission.ts`, `app/native/peer`). The
  bridge is a Unix socket (0600, in a 0700 folder of the user's own that is not a link: in the app's data, or, when that
  path is too long for a socket, a folder of that data folder's own in the user's system temp folder) whose path main
  writes into the vault marker `brain/_index/hud-host.json`. Main knows each agent CLI's process because it spawned it: a Chat turn's directly, and a
  Code launch's as the terminal's own process (above). When an MCP server connects, the app's own Node-API addon reads
  the peer's pid (`LOCAL_PEERPID`), its executable and argv: its script must be the vault's `mcp-server.js` and its
  parent a CLI the app registered while it runs, whose running code is the vendor's (an Apple-anchored signature with
  Anthropic's or OpenAI's team ID, checked on the process, so a file renamed over its path does not count) or an npm
  install (Node running a script inside `@anthropic-ai/claude-code` or `@openai/codex`, with Codex's npm launcher
  allowed between them and its signed binary). The answer to an admitted server lists the names of the tools this app takes, and the runtime sends no other, so an older app is never sent a tool it does not know. The first connection per CLI wins; a second, a server further down (an
  npm script, the agent's own shell commands), a CLI typed by hand into a shell and anything outside the app are refused
  with one line. A Codex Code launch starts with `--no-daemon` while Settings ▸ Computer is on and its CLI's help lists
  it (R70; the help is read with the launch's environment, and a resume line's from `codex resume --help`; main decides
  it again right before it starts the CLI and refuses a line that disagrees, R79, R81): Codex 0.167's TUI
  otherwise runs its MCP servers in a shared background server it keeps running, which the app did not start, so the
  agenticos server there would be refused like any other. The e2e suite's switches (`AOS_E2E_TRUSTED_CLI` naming its stand-in CLIs, `AOS_E2E_HOST_RULES`
  mapping its `*.test` sites to 127.0.0.1, `AOS_E2E_START_PAGE` pointing the start page and its search at a local
  fixture, so no run reaches the real DuckDuckGo) are read only by an unpackaged build (`computer/notify.ts`).
- **The gate holds every input until it may go** (D6, D17, D31, D34, D39, D43; `gate.ts`, `service.ts`, `asks.ts`). One
  session has its own browser (keyed `code:<the terminal's first process>` or `chat:<thread>`; it starts off and only the person turns it on) and drives it one action at a time; a call into a browser gets "busy" while the user has taken over, or while a different agent process is acting in it, its look tools still work. A Read only session can
  look but not act. Opening a page, scrolling, snapshots, screenshots and navigation keys (arrows, Page Up and Down,
  Home, End, Tab, Esc) go freely. On a site the person has not marked, any click, any other key (Space and Return
  included) and any typing asks before the input is delivered; on a marked site the agent acts freely and only the ask
  vocabulary's categories ask (submit, purchase, send, delete, merge, sign-in, download), judged by the control a click
  would actually hit (a key by the focused control, named the same way: its accessible name, markup hint and text). The
  press goes to the point the hit test judged, on a scrolled page too: the page's scroll is read before and after the
  test and again just before the press, and a scroll in between refuses the action.
  Return, or a newline in typed text, asks on every site unless the focus is a plain text area with no key listener;
  downloads, file inputs and permission prompts always ask. A tab is the agent's own only when the agent's own `computer_open` made it (a new tab with `newTab`, or the first tab of a browser that had none; navigating a tab never makes it the agent's own) (or a popup made while the agent held the wheel from such a tab); closing any other tab (a page a program opened, a link the person clicked, the pane's **+**, a restored tab, the start tab an agent's close of the last tab leaves) asks first (`closetab`), and Back, Forward or Reload onto a page that a form loaded, or whose way of loading is not known, asks first (`resend`). An allowed close is bound to that tab and the page it showed, and an allowed Back, Forward or Reload to that tab and that history entry: if the tab shows another page by then, nothing is closed or moved. The agent's close of the last tab leaves the browser on with one new tab at the start page, which is not the agent's own. A held call returns within 45 s of its start
  (`waiting_for_user`, then `computer_wait`, which also picks up an action the person allowed just before then); no
  answer within `computer.askTimeoutSec` is a Deny. An approved action is checked again just before it runs (the same
  session holds the wheel, the same page, tab and element, a focused one by its DOM node and frame, so a same-named
  control does not pass). "Always on <site>" is saved only once that action has been delivered, so an action refused
  then, or one that fails, saves nothing. A key or typing goes only to the tab and page whose focus the gate judged, and
  only while that element still has focus: the tab and page are checked before every key event and every chunk of
  typing, and the focus is read again before every chunk, before every event of a newline's Enter and before every key
  event except the key-up of a free navigation key (Tab, an arrow, Home, End, Page Up, Page Down, Esc), whose own
  key-down moves focus by design. Any other key-up (Space, Enter, a letter) whose key-down moved the focus is withheld and
  the key is reported as moved, and typing stops at the chunk whose input sends the page elsewhere. Every click, key
  event and chunk of typing goes only while its call is still current, checked just before it is sent and after every
  read of the page on the way (opening a page and scrolling, which never ask, are checked when the call starts, so one
  can still land just after a Take over), and a call that is no longer current raises no ask: the session still holds
  the wheel, from the process the app registered for it (a thread's next Chat CLI under the same key is another caller),
  and no Take over, Hand back or end of the turn has come since the call began (each starts a new generation of the
  computer, so a call that waited through a Take over and Hand back sends nothing, though the same session drives
  again). A press's release and a chord's modifier key-ups complete what was already sent: they go when only the page
  moved within its document (a mousedown handler's pushState), when a check stopped the chord on that document, and when
  a key failed to send (letting Shift go activates nothing), but only to the document that got the press and only while
  the call is current. After a cross-document commit, a Take over or a Stop they are withheld. The trade: the page may
  see a press without its release (a mousedown with no mouseup until the person's next click), and a page that tracks

## The door

A program running inside a session (a dev server's "open the browser", `gh auth login --web`, Superpowers' visual companion) can open a page in that session's browser (session-browser S23; `app/src/main/computer/door.ts`, `app/resources/opener/unidex-open.js`). It is a second and much narrower socket than the tools' bridge, and it exists only while the bridge does.

- **What it takes.** One line of JSON: an id and a web address. Nothing else is read. The socket is a Unix socket for this user only (mode 0600, in a folder only this user can enter), made the way the bridge's is.
- **Its limits.** At most 6 pages a minute for a session, a line of 16 KiB, 2 seconds of silence and 16 connections at once; a message over any of them is dropped. The address must be `http:` or `https:` with no user name or password, and is checked again in main.
- **It only opens a page.** It never reads a page, clicks or types, and answers nothing about the browser. The page opens as a new tab of the session named by the id: on a browser that is on with no question, as `computer_open` does (while the person holds the wheel after Take over, the tab opens in the background: it joins the strip and the tab the person is on stays in front); on an off browser through the same Turn on card an agent's open raises (a session has one such card at a time, an agent's or a program's; up to 6 addresses wait behind it, and Not now opens nothing and quiets that session: for 60 seconds on Code, until the live turn ends on a thread, and for 60 seconds on a thread with no turn live); dropped, and logged, while the session's agent is Read only. With `computer.enabled` off a new session gets none of the three variables and a knock is answered so the opener passes the page on to the previous `BROWSER` or the system's opener; nothing is logged. Read only is guarded twice: a Read only agent's processes get none of the three variables, however it was launched (a chat turn, a Code agent main starts, or the typed-line fallback shell), so no program it leaves behind holds an id after the turn ends, and the session's live agent is checked again when a page arrives. A session the app does not hold gets no browser. A dropped open is logged with the session and the reason, never the address or the id.
- **The id's life.** It is made per session when the session's first process is started, moves with the terminal when it hands over to its replacement, whether or not the browser moved, ends with the session (a closed terminal, a deleted thread), and ends for every Code session when the app's page closes or reloads. It lives only in that session's environment; it is never written to a log or a file.
- **The three variables.** None while Settings › Computer is off (a session started then keeps its own `BROWSER`) and none for a Read only spawn. `BROWSER` and `BRAINSTORM_OPEN_CMD` name the opener, and `AOS_BROWSER_SESSION` carries the id, the socket and the `BROWSER` that was set before. A program can always ignore them, and then it opens the default browser as it did before UniDeX; the variables are a courtesy to programs that honour them, not a boundary. The id lets a process the session started (or any process that can read its environment, as the user's other programs could) open a page in that browser, which is all it allows.
- **When the app cannot be reached,** or the door refuses to connect, or the door answers that it is off (Settings › Computer was switched off after the session started), the opener passes the address on to the `BROWSER` that was set before, else to the system's opener, as if UniDeX were not there. An address that is not `http` or `https` is never sent to the door: it goes to the previous `BROWSER` or the system's opener. Once the door has answered, a refused or dropped open (the limit, Read only, the quiet period) is not passed on anywhere: nothing opens. When the door gives no whole answer (the connection ends, fails or stays silent for 3 seconds) nothing is passed on either, because the door may have taken the address: the opener exits 1 with one line on standard error and the agent opens the address with `computer_open`. A host's command sandbox (Codex's, with network access off) may refuse the socket itself: the opener then prints a one-line notice and nothing opens through it; the agent opens the address with `computer_open`.
