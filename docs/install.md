# Install

UniDeX runs on **macOS** with Node 20+ and uv, which `aos init` checks before it writes anything; Ollama (macOS 14 or later) runs its background work on your Mac, and Claude Code and/or Codex CLI (logged in) are the hosts your sessions run in, and optional at install. The app's setup installs every one of them itself. The Workbench is the **UniDeX** app, a macOS app for Apple silicon (macOS 13 or later) that reads the vault the installer records; Obsidian is not needed (the vault stays plain Markdown, so any editor still opens it). Coming from a release before 1.0, where the Workbench ran in Obsidian? See [migrating-to-1.0.md](migrating-to-1.0.md). The runtime's Linux code (cron schedules) is still there but untested and unsupported; Windows is not supported.

## From the app

Download `AgenticOS-Workbench-<version>-arm64.dmg` from the [latest release](https://github.com/zzoretich/UniDeX-Agent-Harness/releases/latest), open it, drag **AgenticOS Workbench** to Applications and open it. The app is signed and notarized.

Opened with no install, the app runs this same install for you, with nothing installed beforehand: no Homebrew, no Node, no terminal. Its setup wizard checks Node, uv, Ollama and its models, and both hosts and their logins, and installs what is missing itself: each missing tool's button downloads a version pinned in the app from its maker (Node from nodejs.org, uv, Ollama and Codex from their GitHub releases, Claude Code from its own download site), checks the download's SHA-256 against the pin and its maker's code signature (and Gatekeeper, for the Ollama app) before installing anything, and shows its progress; a download that does not match is deleted, and the button offers **Retry**. **Install what's missing** runs Node, uv, Ollama and its models one after another. Where each goes: Node into `~/.local/share/unidex/node/<version>` with a `current` link, which `agenticos.json` records; uv into `~/.local/share/unidex/uv/<version>`, linked from `~/.local/bin`; the Ollama app into `/Applications` (else `~/Applications`), opened in the background; Claude Code through its own installer (`claude install`, into `~/.local/bin`); Codex as its own installer lays it out (`~/.codex/packages/standalone`, linked from `~/.local/bin`). A tool you already have is used as it is, when it is new enough and answers with its version, and anything already where a tool goes that is not the installer's own is moved aside to `<name>.unidex-backup-<time>`, never replaced. Ollama's models follow your Mac's memory: under 12 GB `qwen3.5:4b`, otherwise `qwen3.5:9b`, plus `qwen3-embedding:0.6b`, pulled through Ollama's own API with its progress; Continue never waits for Ollama or its models. Logging in (`claude auth login`, `codex login`) runs in a terminal inside the wizard, so you see the command and can type the code it asks for. It then asks which hosts (**No agent CLI yet** is always offered, and chosen for you when neither is installed and logged in: it installs without one, and Sessions and the Chief of Staff wait until you add Claude Code or Codex), which vault folder, and the Chief of Staff questions in a form, and runs `aos init --yes` from the runtime the app carries in `Contents/Resources/payload`, whose dependencies come with it (no npm). Finish lists what is left, step by step: for Claude Code the `CLAUDE.md` line as a diff, added only if you say so; for Codex the `/hooks` trust; with no host, how to add one; and **Add aos to my PATH**, which shows the one line it appends to `~/.zprofile` (`export PATH="$HOME/.local/bin:$PATH"`) and writes it only while ticked. It ends in the Workbench.

With an install, the app opens it. When the app carries a newer runtime than the vault has (after the app updates itself), it offers to run `aos upgrade` from that runtime, never on its own. `node "/Applications/UniDeX.app/Contents/Resources/payload/cli/aos.js" upgrade` does the same from a terminal. The app updates itself from the same releases (UniDeX ▸ Check for Updates…; `updates.check: false` turns it off, as it does the runtime's update check).

The terminal path below does the same install from a checkout.

## Ten-minute path

```
git clone https://github.com/zzoretich/UniDeX-Agent-Harness.git
cd UniDeX-Agent-Harness
npm ci --ignore-scripts
npm run setup            # = node cli/aos.js init
```

While developing from a checkout, run `npm run setup -- --from-local .` so the plugin is installed from your clone rather than from GitHub.

`aos init` runs these steps in order. After the preflight passes, it asks for a vault directory (default `~/AgenticOS`; not asked with `--vault`, `--yes` or `--dry-run`, or when stdin is not a terminal). It refuses `~/.claude`, any directory holding a `settings.json`, your home directory, a filesystem root and the Codex home:

1. **Preflight** — Node ≥ 20; uv (on PATH, or in `~/.local/bin` or `~/.cargo/bin`); the hosts (see [Hosts](#hosts)): `claude` on PATH and logged in (`claude auth status`) and/or `codex` on PATH and logged in (`codex login status`), or none with `--host none`. A missing prerequisite exits 1 with an install hint and nothing is written. Ollama (`ollama` on PATH or `Ollama.app`) is a warning, not a requirement: background work waits for it; install it from ollama.com. python3 ≥ 3.9 is checked only with `--cost`, the one thing that runs it (graphify's Python comes with uv). `--provider none` does not waive Node, uv, or a missing `codex` CLI when Codex is a host. It does let init continue with a warning when the `claude` CLI is missing (the plugin step is skipped) or logged out (the plugin install is still tried and may fail), or when `codex` is logged out. Whether Ollama answers on `127.0.0.1:11434` is printed, not required.
2. **Seed** — copies `vault-template/` (existing files are kept) and writes `brain/config.json` from the shipped defaults.
3. **Vendor the runtime** — `brain/scripts` (without tests or a lockfile) into `<vault>/brain/scripts`, plus every non-test `cli/*.js` (`aos.js` and the modules behind its subcommands and helpers: `persona-cmd.js`, `schedule.js`, `routines.js`, `cost-cmd.js`, `graph-cmd.js`, `workspace.js`, `codex-host.js`, …; no tests, fixtures or rehearsal), the plugin's `commands/` and `skills/` (→ `brain/scripts/plugin/`, which the Codex host generates its skills from), the persona templates (`vault-template/persona/` → `brain/scripts/persona/templates/`), the schedule and cost sources (`extras/{schedule,cost}/` → `brain/scripts/extras/`, without the python tests) and the `aos` launcher; then `npm install --omit=dev` there (two dependencies, pinned by `^` ranges); symlink `~/.local/bin/aos` → `<vault>/brain/scripts/bin/aos`. `aos upgrade` refreshes the same set, and `aos doctor` checks that the persona and schedule pieces are present.
4. **`~/.claude/agenticos.json`** — vault, node path (for a Homebrew Node, the stable `<prefix>/opt/<formula>/bin/node` link rather than the versioned `Cellar/` path `brew upgrade` deletes, and for the app's own Node its `current` link; the routine schedules use the same path), config dir, the resolved `claude` path (`claude.bin` — hooks, the MCP server and the Workbench app spawn it without a login shell; `aos upgrade` re-resolves it, and a recorded path that no longer exists is ignored), the `hosts` block (which of Claude Code and Codex are wired, their config dirs and binaries), provider (`local` for a new install; an existing file keeps its value), spend caps, telemetry, cost, persona flags. Honors `CLAUDE_CONFIG_DIR` (and `AOS_CONFIG` for an explicit file path — the same rule every hook and `aos` subcommand uses).
5. **graphify** — with `--cost`, first the cost module (as `aos cost enable` would; see `docs/cost.md`). Then the pinned graphify, installed through uv into `~/.local/share/agenticos/graphify` (`$XDG_DATA_HOME/agenticos/graphify` when set; never your own uv tools or PATH) and recorded as `graph.bin` in `agenticos.json`. It copies `<vault>/.graphifyignore` from the template when the vault has none, and adds the graph's output folder to the vault's `.gitignore` when that file exists.
6. **Plugin** (Claude Code host) — `claude plugin marketplace add zzoretich/UniDeX-Agent-Harness` then `claude plugin install agenticos@agenticos-workbench`. With `--from-local <repo-dir>` the marketplace source is your checkout. **Codex host** — `codex plugin marketplace add zzoretich/UniDeX-Agent-Harness` (your checkout with `--from-local`) then `codex plugin add agenticos@agenticos-workbench`, when the Codex CLI installs plugins; otherwise the direct wiring: five hook entries merged into `<codex home>/hooks.json`, `codex mcp add agenticos --env AOS_CONFIG=<agenticos.json> --env AOS_HOST=codex -- sh <vault>/brain/scripts/bin/aos mcp-server`, and the 21 commands plus 9 skills generated into `~/.agents/skills/<name>/SKILL.md` from the vendored `brain/scripts/plugin/`; see [Hosts](#hosts).
7. **Chief of Staff interview** (skipped with `--host none`: its duties need a host) — names your agent and writes `<vault>/persona/` (identity, state, playbook, five duties — monitor, reflect, reflect-daily, sitrep and tick — and a proposals README), and seeds the persona's own routines (heartbeat, reflect-daily, tick) into `brain/routines/` beside the monitor, reflect and sitrep routines from the seed step; files already there are kept. With `schedule: yes` it also installs a launchd schedule for every enabled routine in `brain/routines/`: six on a fresh vault, including the 30-minute heartbeat and the hourly tick. `aos routines` manages them afterwards. `--persona-json <file>` answers it non-interactively (fields `name`, `addressAs`, `voice`, `priorities`, `dutyModel`, `dutyCodexModel` (Codex host only; stored as `persona.codexModel`), `dutyEffort`, `schedule`) — use it in CI and wherever stdin is not a terminal. With `--yes` (or no terminal) and no `--persona-json`, init reuses `<vault>/persona/answers.json` from an earlier run, or skips the interview with a note and continues; run `aos persona` later. Details: `docs/chief-of-staff.md`.
8. **First scan** — `scan-vault` (which also builds the vault graph), `build-brain-md`, `recall --warm`.
9. **Checklist** — every file written, the line to add to your `CLAUDE.md` (Claude Code), the hook entries to trust under `/hooks` (Codex), and how to open the Workbench.

Then add the printed line to `~/.claude/CLAUDE.md` (the installer never edits it):

```
@/path/to/AgenticOS/AGENTICOS.md
```

Under Codex there is nothing to paste: a SessionStart hook injects `AGENTICOS.md` itself. Open `codex`, run `/hooks`, and trust the agenticos entries once.

Open the **AgenticOS Workbench** app (download it from the [latest release](https://github.com/zzoretich/UniDeX-Agent-Harness/releases/latest); it finds the vault through `agenticos.json` and records itself in `<vault>/brain/_index/hud-host.json` for `aos doctor` and the update check), and start a new `claude` or `codex` session: the first prompt receives `<brain-context>`, `/wrap` (`$agenticos:wrap` under Codex) writes memories, and the `agenticos` MCP server answers `recall`.

Flags: `--vault <dir>`, `--host auto|claude|codex|both|none` (default `auto`: an existing install keeps its selection, a fresh one wires every host that is installed and logged in; `none` installs the vault, the runtime and the background work with no host, and running `aos init --vault <the same vault> --host claude|codex|both` later adds one and keeps every file: `--host` names the whole set, so to keep Codex while adding Claude Code say `both`; a `--host` that would turn off a host the install has wired is refused before anything is written, since init never unwires one: `aos uninstall --host <host>` does), `--provider local|auto|ollama|claude|codex|none`, `--cost [--budget <usd>]` (installs the cost module; `--budget` sets its monthly budget, and without it init asks unless `--yes`), `--persona-json <file>`, `--from-local <repo-dir>`, `--dry-run` (prints the numbered plan, writes nothing; besides `init`, only `aos routines run`, `aos skills sync`, `aos agents sync` and `aos config set|unset` take it; `aos upgrade` and `aos uninstall` reject it as a usage error), `--yes` (accept defaults, no prompts). `--flag=value` works too. Any unknown or misspelled flag is a usage error (exit 2), so a typo never starts a real install. `--no-obsidian` and `--terminal`, from releases that installed the Obsidian HUD, are still accepted and do nothing. Re-running `aos init` on an existing vault keeps your files and your provider setting; only an explicit `--provider` changes it.

Every runtime script is also reachable as `aos <name>` (`aos scan-vault`, `aos recall "<query>"`, `aos build-brain-md`, …); the same launcher is what the plugin's hooks call as `sh "${CLAUDE_PLUGIN_ROOT}/bin/aos" <name>`.

**Orphan sweep (off by default).** `<vault>/brain/_index/scanner-config.json` ships with `"autoSweepOrphans": false`. Set it to `true` and every `scan-vault` run (the SessionEnd hook, `aos scan-vault`, `aos init` / `aos upgrade`, and the Workbench's periodic snapshot refresh) removes the per-session side-folders Claude Code leaves behind — and nothing else. The sweep looks only at UUID-named directories directly under `session-env/` and `file-history/` in the Claude config dir recorded in `agenticos.json` at install (`~/.claude` unless `CLAUDE_CONFIG_DIR` was set when you ran `aos init`); it removes one only when that UUID has no `<uuid>.jsonl` transcript under any project in that config dir's `projects/`, only once the directory is older than `orphanUuidMinAgeMinutes` (60), and only when it is empty. With `sweepTransientResidue` on, a directory holding nothing but files matching `transientResiduePatterns` is removed too; the template ships that off (`false`, no patterns), but a hand-written `scanner-config.json` that omits both keys gets the code default — on, with the built-in `-hook-<n>.sh` pattern. If `projects/` itself cannot be read, the sweep does nothing and the snapshot's `maintenance.orphanSweep` carries `reason: "projects-unreadable:<code>"`, rather than treating an unreadable allow-list as an empty one. It never touches the vault (memory, notes, persona), Claude Code's transcripts, or anything outside a UUID-named orphan directory.

**Daily-note layout.** `dailyNote.layout` in `<vault>/brain/config.json` (default `{yyyy}/{yyyy}-{MM}-{MMMM}/{yyyy}-{MM}-{dd}.md`; tokens `{yyyy}` `{MM}` `{MMMM}` `{dd}`) is the one place the layout lives: the scripts and the Workbench's Brain map (Every node) read it. Every surface lists exactly the notes that match it — recall, `session_list`, `/standup`, `/reflect-week`, the session count and streak in the snapshot, and the graph's session nodes. Change the layout after notes exist and the old notes drop out of all of them (the streak resets) until you move them into the new shape; a layout with no `{dd}` anywhere in it matches nothing (the day may sit in a folder segment, e.g. `{yyyy}/{MM}-{dd}/notes.md`); symlinked year or month folders are not followed; a `{MMMM}` folder must carry the full English month name.

## Bring in your history

`aos import` reads what you already have on disk, for whichever host left files there (its CLI need not be installed any more), through the same host folders the rest of the runtime uses, and never sends any of it to a hosted model (spec 2026-10-14-install-and-import, B3–B10, B15):

- **Instructions.** Claude Code's global `CLAUDE.md` (in its config folder) and Codex's `AGENTS.md` / `AGENTS.override.md` (in its home) are split by heading and bullet into rules. With the local model ready, each rule becomes a memory typed user, feedback or reference; without it, each file becomes one reference memory. An `@path` include line (the `@<vault>/AGENTICOS.md` line among them) is never copied, nor is a file inside the vault; a project's own `CLAUDE.md` / `AGENTS.md` stays in its repository, which its workspace links through `repo:`.
- **Memories.** Claude Code's auto-memory (`<claude config dir>/projects/*/memory/*.md`, its `MEMORY.md` index left out) keeps its type. Codex's built-in memories stay Codex's.
- **Projects.** Folders your sessions ran in outside any workspace, grouped by git repository, are proposed as workspaces named after the repository, with `repo:` set, when the repository had 3 or more sessions in the window or any in the last 14 days (a workspace of that name already there gets the folder as its `repo:`, or as an alias when it has one). A real run creates only the ones you pass with `--accept '["~/code/app"]'` (the ids the scan prints, or `{ "id": …, "name": … }` to rename one); without it, it creates none and says so.
- **MCP servers.** Both hosts' user-scope servers (Claude Code's `.claude.json` `mcpServers`, Codex's `config.toml` `[mcp_servers]`) are listed in `brain/_index/mcp-servers.json`: name, host, transport, the program or URL, never their arguments, environment, headers or query strings. No host config is written.
- **Sessions.** The window's interactive sessions (90 days by default, `--since all` for everything; not headless runs, team seats or Sessions threads, and not one active in the last hour) are queued for the **import-digest** routine, which `aos import` turns on.

Every memory is written with `source: import:<host>`, `origin: ~/…` (the file it came from) and `reviewed: false`, after a duplicate check against your memories (the same text, a like title or like words, and like meaning when an embed index is there), so Brain ▸ Review shows one "Imported from Claude Code" and one "Imported from Codex" batch. `brain/_index/import-state.json` records each phase and the hash of everything imported, so running it again writes nothing twice.

**The digest** (`brain/routines/import-digest.md`) runs every 30 minutes while sessions wait, up to 10 minutes a run, one session at a time on the local model only. It asks for a one-line summary, the workspace (when the session's folder did not already say) and at most three memories, and writes a `## Sessions` line into that day's daily note (the note is created when there is none; an existing one only gains the line), a newest-first timeline in `workspaces/<ws>/history.md`, the memories, and `brain/_index/session-digests.json`. It marks each session in auto-wrap's offsets, so a later wrap of the same session extracts only what came after. On battery (`local.onBattery: defer`, the default), or while the local model is down or not pulled, it waits and spends nothing; a session it cannot summarise gets its title instead. When the queue is empty it turns itself off (the next `aos routines sync`, or Apply in Routines, takes the schedule out), and the next `aos import` turns it on again. Progress is in `import-state.json` (`digest.processed` of `digest.total`).

## Hosts

A *host* is the agent CLI a session runs under; a *provider* is the model that answers background questions. They are independent: a Codex-only machine can still use Ollama, and a two-CLI machine keeps one vault, one memory pipeline and one set of hooks.

**Three modes, one runtime.** Claude Code only, Codex only, or both on one vault behave the same: context on the first prompt, working memory on every stop, telemetry, costing and memory extraction at the end, the Chief of Staff and the routines in between. What differs is only how each host is wired (below) and how the runtime learns which host it is serving:

1. `AOS_HOST` in the environment — set by every Codex hook entry and by the Codex MCP server's entry, in the Codex plugin and in the direct wiring alike, and by the Claude Code plugin's MCP server entry (`claude`), so the server tags the memory-usage rows it writes; Claude Code's hooks set nothing and claude is the default;
2. else Claude Code's own hook environment (`CLAUDE_PROJECT_DIR`);
3. else the session transcript named in the hook payload (`rollout-*.jsonl` under the Codex home is Codex; a file under `<claude config dir>/projects/` is Claude Code);
4. else the `hosts` block when exactly one host is enabled;
5. else Claude Code.

`AOS_DEBUG=1` prints the chosen host and the rule that chose it. Related keys in `brain/config.json`: `telemetry.staleAfterMinutes` (default 30: a live run idle that long is reconciled, see below), `persona.runner` and `routines.runner` (`auto` | `claude` | `codex`, which CLI runs duties and prompt routines).

| Key | Meaning |
|---|---|
| `hosts.claude.enabled` | Claude Code is wired: the plugin is installed, doctor checks its login and plugin, `CLAUDE.md` is expected. |
| `hosts.claude.configDir` · `hosts.claude.bin` | Its config dir (mirrors `claudeConfigDir`) and the resolved CLI (mirrors `claude.bin`). |
| `hosts.codex.enabled` | Codex CLI is wired (below). Also what lets the `codex` provider join the `auto` chain. |
| `hosts.codex.home` · `hosts.codex.bin` | Its home (`CODEX_HOME`, default `~/.codex`) and the resolved CLI. |
| `hosts.codex.install` | `plugin` or `direct`: how the host is wired (below). Written by `aos init` and `aos upgrade`. |

**Skills on both hosts.** The two CLIs read user skills from different folders: Claude Code from `<claude config dir>/skills/` (plus the claude.ai-synced ones under `skills/synced/`), Codex from `~/.agents/skills/`. With both hosts enabled, the `skills-sync` SessionEnd hook (on both hosts, detached) copies each host's own skills into the other host's folder: a translated `SKILL.md` (Codex needs `name` and `description`; `$ARGUMENTS`, the question tool and `/name` ⇄ `$name` references are rewritten), a symlink for each supporting file, and a `.aos-mirror.json` sidecar. A folder without that sidecar is never written or removed, and a copy you edited by hand is left alone until `aos skills reset <name>`. Plugin skills and built-ins are listed (`aos skills list --all`, the Skills tab) but never copied: they need their plugin's tools. `aos skills exclude <name>` stops sharing one (`skills.exclude` in `brain/config.json`); `skills.sync: false` stops it all. Codex lists skills within a budget of about 2% of its context window and shortens descriptions, then drops skills, beyond it; exclude the ones you never use in Codex if it warns. After `aos upgrade`, Codex asks you to trust the new `skills-sync` hook entry once under `/hooks`.

**Agents on both hosts.** The two CLIs keep custom subagents in different folders and formats: Claude Code reads `<claude config dir>/agents/<name>.md` (YAML frontmatter; the body is the prompt), Codex reads `<codex home>/agents/<name>.toml` (`name`, `description`, `developer_instructions`; subagents are on by default, `features.multi_agent`). With both hosts enabled, the same `skills-sync` SessionEnd hook then copies each host's own agents into the other host's folder, so there is no extra hook to trust. The copy carries the name, the description and the prompt, with a note that maps the other host's tool names; a Claude Code agent whose `tools` cannot write (no `Write`, `Edit`, `MultiEdit`, `NotebookEdit` or `Bash`) becomes `sandbox_mode = "read-only"`, and the reverse; the model, effort, colour, MCP servers and hooks stay behind, so each host uses its own default model. Each copy carries an `# aos-mirror:` comment: a file without it is never written or removed, and a copy you edited by hand is left alone until `aos agents reset <name>`. A name that would replace a host's built-in agent (Codex `default`, `worker`, `explorer`; Claude Code `general-purpose`, `explore`, `plan`, …) is never copied. Claude Code plugin agents and roles declared in Codex's `config.toml` (`[agents.<name>]`) are listed (`aos agents list --all`, the Agents tab) but never copied. `aos agents exclude <name>` stops sharing one (`agents.exclude` in `brain/config.json`); `agents.sync: false` stops it all. Codex sends every agent's description with each turn, so exclude the ones you never use there. To use an agent: in Claude Code ask for it, mention `@agent-<name>`, or run `claude --agent <name>`; in Codex ask for it by name.

**The status line on both hosts.** `aos statusline install` is opt-in and writes only to the hosts you enabled (`--host` picks one). Claude Code: `statusLine` and `subagentStatusLine` in `<claude config dir>/settings.json` run the vault's launcher (`sh '<vault>/brain/scripts/bin/aos' statusline render`), and the status line that was there is recorded and chained. Codex: `[tui] status_line` in `<codex home>/config.toml` gets a preset of built-in items, because Codex runs no status line command; the SessionStart `update-notice` hook prints what needs you instead, so no hook is added and nothing needs re-trusting under `/hooks`. Both files are copied to `<file>.aos-statusline.bak` before the first write, install state is kept in `agenticos-statusline.json` beside `agenticos.json`, and `aos statusline uninstall` (and `aos uninstall`) restore both files.

**The Codex plugin.** When the Codex CLI installs plugins (`codex plugin list --json` answers), `aos init --host codex` installs `agenticos@agenticos-workbench` from this repository's marketplace. Codex reads `.agents/plugins/marketplace.json` before `.claude-plugin/marketplace.json`, so the one repository gives Claude Code `plugin/` and Codex `codex-plugin/`. `codex-plugin/` is generated from `plugin/` by `npm run build:codex-plugin` and committed; a test fails when it drifts. It carries:

- `hooks/hooks.json` — the same entries as the direct wiring below, each command `env AOS_HOST=codex sh "${PLUGIN_ROOT}/bin/aos" <name>`. Codex expands `${PLUGIN_ROOT}` to the installed plugin folder but checks trust against the command as written, so a trusted entry stays trusted when the plugin is upgraded.
- `.mcp.json` — the `agenticos` server as `sh ./bin/aos mcp-server` with `cwd: "."` (Codex expands no variable in MCP arguments and resolves `.` to the plugin folder), `AOS_HOST=codex`, and `AOS_CONFIG` / `CLAUDE_CONFIG_DIR` passed through when you set them.
- `bin/aos` — the launcher, a byte copy of `plugin/bin/aos`. Nothing in the plugin names a path on your machine: the launcher finds `agenticos.json` the way it always does (`AOS_CONFIG`, else `${CLAUDE_CONFIG_DIR:-~/.claude}/agenticos.json`).
- `skills/` — the 21 commands and 9 skills of `plugin/` as Codex skills, listed as `agenticos:<name>` (`$agenticos:wrap`, `$agenticos:remember`, …), with every Claude Code idiom rewritten; the launcher is `<plugin root>/bin/aos`, two folders above each skill's folder.

Once the plugin is installed, `aos init` and `aos upgrade` remove any direct wiring (below) so the two never run side by side, and an existing direct install moves over on its next `aos upgrade`. A plugin install that fails falls back to the direct wiring, and the next upgrade tries again.

**What the direct wiring writes** (a Codex CLI without plugins). Codex has a hook system shaped like Claude Code's, so the runtime is shared and only the wiring differs:

- `<codex home>/hooks.json` — one entry per event (SessionStart, UserPromptSubmit, PostToolUse, Stop, SessionEnd), every command `env AOS_HOST=codex AOS_CONFIG='<agenticos.json>' sh '<vault>/brain/scripts/bin/aos' <name>`. That prefix is how `aos` recognises its own entries: your own hooks in the same file are never touched, and the file is deleted on uninstall only when nothing else is left in it. SessionEnd entries carry Codex's 3 s cap (every handler hands its work to a detached process). SessionStart additionally runs `inject-conventions`, which prints `AGENTICOS.md` as session context on startup, resume, clear and after compaction — Codex's `AGENTS.md` has no include syntax.
- `codex mcp add agenticos …` — the same MCP server, registered in Codex's `config.toml`; its tools appear as `mcp__agenticos__<tool>`. Every read tool advertises the read-only annotation Codex needs to call it inside a sandbox without an approval prompt.
- `~/.agents/skills/<name>/SKILL.md` — one skill per plugin command and skill (`$wrap`, `$remember`, `$recall`, …), generated from the vendored `brain/scripts/plugin/` with every Claude Code idiom rewritten (launcher path, config path, MCP tool names, arguments). A generated file carries a marker comment; a skill directory of the same name that you wrote yourself is left alone and reported.

**Trust.** Codex quarantines hooks until you have reviewed them: open `codex`, run `/hooks`, and trust the agenticos entries once. They keep their trust across `aos upgrade` because the command text never changes (plugin entries never name a path; direct entries name the vault's launcher, so only moving the vault changes them). Moving from direct wiring to the plugin asks once more, since the entries themselves are new.

**What differs from Claude Code.** Codex reports tool payloads as JSON strings (handled); fires SessionEnd late in its TUI (thread close or archive, or 30 minutes idle) and, depending on the version, not at all when `codex exec` exits (0.144 did not, 0.155 does); and keeps its own built-in *memories* feature, which `aos` neither reads nor disables (doctor shows an info row when it is on). The late SessionEnd is covered by `reconcile-sessions`, a hook on SessionStart and Stop of both hosts: it finds every live run whose telemetry, live file and transcript have all been idle for `telemetry.staleAfterMinutes`, closes the run (ended at the transcript's last change), then costs and wraps it exactly as SessionEnd would have. A Codex run does not wait that long once you quit: its telemetry header records the Codex process the session runs in, and the first sweep after that process has exited (the next session start or stop of either host, at most one sweep per 5 minutes) closes the run at once. When the process cannot be identified (no `ps`, or the desktop app's long-lived daemon), the idle rule applies. A real SessionEnd that arrives later finds nothing to do. `$wrap` in-session is always immediate.

**Workspaces on both hosts.** Spaces and `aos workspace` read each host's sessions from that host's own folders (Claude Code's `<claude config dir>/projects/`; Codex's `sessions/`, `archived_sessions/` and `session_index.jsonl` under its home), and where the hosts differ the difference is recorded, not evened out (spec 2026-10-09-spaces-redesign D34):

- **One 30-day window.** Session counts cover the last 30 days (`workspaces.idleDays`) on both hosts. Claude Code deletes transcripts older than its `cleanupPeriodDays` setting, 30 days by default, while Codex keeps its rollouts for months, so a longer window would count Codex's history and not Claude Code's. A `cleanupPeriodDays` below 30 shortens what Spaces can count for Claude Code.
- **Titles per host.** Claude Code: the title you gave the conversation, else the one it generated. Codex: the thread's `thread_name` in `session_index.jsonl` (the newest after a rename). Either host: the first prompt when there is no title.
- **What files-based credit sees.** A session started at the vault root counts for the workspace whose files it touched most (at least 3 touches and no tie; `workspaces.attributeByFiles`). For Claude Code that is the paths of its Read, Edit, Write, MultiEdit and NotebookEdit calls and each entry's folder, but not what a subagent touches (its transcript under `<id>/subagents/` is never read). For Codex it is the files its patches change and each turn's folder, with a `thread_spawn` subagent's edits folded into its thread; files a shell command reads carry no path, so a Codex session that only reads earns no credit.
- **Resume.** `claude --resume <id>` finds a vault-root thread from a workspace folder (checked with Claude Code 2.1.296), so both hosts resume in the workspace's folder, or its linked code folder. Codex resumes with `codex resume -C <folder> <id>`, which takes any recorded session, a `codex exec` run included (`--include-non-interactive` only filters the picker and `--last`; checked with codex-cli 0.162.0), and keeps the thread's own sandbox and approval. A thread credited through a git worktree resumes in that worktree while it exists. A Claude Code headless run (`sdk-*`) and a thread archived in Codex are not resumable, and Spaces says why. The team ledger records each Codex seat's thread id, as it does Claude Code's session id.
- **In-session writers under Codex's sandbox.** `$agenticos:todo`, `$agenticos:propose` and `$agenticos:project` (`$todo`, `$propose`, `$project` with the direct wiring) and every `aos workspace` verb except `list` and `which` write vault files (`TODO.md`, `persona/proposals/`, `brain/memory/projects/`, `workspaces/`, `brain/_index/`: `new` and `stubs` a workspace folder, `adopt --into` and `set` its `workspace.md`, `hide` and `unhide` the hidden list, `draft` the provider state and the spend ledger, and each writing verb the snapshot). From a session that runs in a workspace's folder, or in a linked code folder outside the vault, those files lie outside the session's folder, so a `workspace-write` sandbox may ask you to approve the write; `aos workspace which` only reads. The Spaces tab runs the same verbs from the app, outside any session's sandbox, so its buttons never ask.
- **Draft workspace.md** makes one call through the provider chain: Ollama, then a logged-in `claude` CLI (whether or not Claude Code is an enabled host), then Codex (`codex.model` at `codex.effort`, run from an empty temporary folder, the daily cap gating its start; `aos provider codex` puts it first). The dialog names who answered; under `none`, at a cap or on a bad reply the draft is a labelled heuristic. Inside a Codex session the `workspace-write` sandbox has no network, so `aos workspace draft` run there gives the labelled heuristic: use Draft in Spaces, which runs from the app.

**Cross-review between the hosts.** `/cross-review` (`$agenticos:cross-review`) sends a plan to the *other* CLI for an independent review, and `/handoff` (`$agenticos:handoff`) runs one scoped task on a model you choose. Each call is one child session through `aos cross-review` (`brain/scripts/cross-review/runner.js`): `codex exec` in the read-only sandbox, or `claude -p` in safe mode with only Read/Glob/Grep; a build uses `workspace-write` or `acceptEdits` instead. No child in any mode gets an MCP server, a plugin or a connector: under Codex every plugin is off (which removes its connectors), each server your `config.toml` declares is switched off by name, and web search, our hooks and the app, browser, computer and image tools are off too; under Claude the MCP config is empty and strict. Every child is ephemeral, so no reviewer transcript reaches either host's session folders or the memory pipeline. An approval is bound to the plan's SHA256; the run records land in `brain/_index/cross-review/` and the spend in the ledger as `cross-review:*`, capped by `crossReview.perDayUsd` (default 10; `crossReview.perCallUsd` also caps each Claude call). `crossReview.claudeModel` and `crossReview.codexModel` (default `null`, each CLI's own default) pick the models. Cross-provider review needs both CLIs installed and logged in, whether or not both are wired as hosts; with one, `aos doctor` says `same-provider only` and the skill offers a fresh session of the same CLI, labelled as such.

**Headless jobs on Codex.** The Chief of Staff duties and `prompt` routines run through `claude -p` when the Claude host is enabled and the CLI resolves, otherwise through `codex exec -` (prompt on stdin, `workspace-write` sandbox, our hooks off, JSON events on stdout). Codex has no per-run budget flag and no tools allowlist: the daily caps (`persona.perDayUsd`, `routines.perDayUsd`) still gate every start, the spend is *estimated* from the usage block and ledgered with `provider: "codex"`, and the sandbox is the guard. `persona.runner` / `routines.runner` (or `AOS_RUNNER` for one run) pin a CLI; `aos doctor` shows the resolved runner per kind, and `run-duty.sh <duty> --dry-run` prints the exact command. On Claude Code a duty runs on `persona.model` (`claude-opus-5-5` on a new install; a `null` left by an older one means the interview's answer, else `claude.model`) at `persona.effort`, and a duty's routine file can set its own `model:` / `effort:`. On Codex a duty runs on `persona.codexModel` (`gpt-6-sol` on a new install; `null` means `codex.model`, else your Codex default) and a prompt routine on `routines.codexModel` (`null` by default); the persona interview asks for the duty model on a Codex host. With both hosts, `persona.failover` (on) moves a duty that cannot start on its host — CLI missing or signed out — to the other host's model (`persona.perDayUsd` is one cap over both hosts: a capped day is skipped, never moved); with none able to start it, it is skipped (journalled `SKIPPED waiting-for-host`, flagged once a day). The HUD's Chat tab answers through the reasoner below, so it works on a Codex-only machine too.

## Providers

`auto` picks Ollama when it answers, else headless Claude when Claude Code is an enabled host (`claude -p --model haiku`, ≤ `claude.perCallUsd` per call and ≤ `claude.perDayUsd` per day, every call ledgered in `brain/_index/provider-spend.jsonl`), else headless Codex when Codex is an enabled host (`codex exec` with the prompt on stdin, ephemeral, read-only, hooks off; the spend is *estimated* from the usage block, since Codex reports tokens and never dollars, and ledgered the same way against `codex.perDayUsd`), else `none`. Under `none` nothing calls a model in the background: summaries are heuristic, and `/wrap` extracts memories in your own session through the `wrap_session` tool. Ollama itself is a prerequisite; the two models it runs, about 7.2 GB together (`qwen3.5:9b`, the workhorse, 6.6 GB; `qwen3-embedding:0.6b`, the embedder, 639 MB), are downloaded by the app's wizard but not by `aos init`. From a terminal, pull them once with `ollama pull qwen3.5:9b` and `ollama pull qwen3-embedding:0.6b`; from a checkout, `sh extras/ollama/model-pull.sh` does both. Then keep `ollama serve` running (or open Ollama.app). `auto` switches to Ollama with no reconfiguration as soon as it answers, without checking for the models, so pull them first.

**The reasoner role.** `/ask-brain --local`, `/reflect-week`, `/consolidate-memory` and the Workbench's Chat tab call the *reasoner*, a hosted model whatever `auto` resolved for the background hooks. Claude first, when Claude Code is a host and logged in: `claude -p --model <reasoner.model> --effort <reasoner.effort>`, ≤ `reasoner.perCallUsd` per call. Otherwise Codex, when it is a host and logged in: `codex exec` on `reasoner.codexModel` (default `null`: `codex.model`, else your Codex default) at `reasoner.effort`, spend estimated. An explicit `provider: codex` puts Codex first. Either way ≤ `reasoner.perDayUsd` per day, ledgered as `reason:<command>` rows that never count against the hook cap. With neither host available, or the reasoner cap reached, and Ollama up, the call falls back to the workhorse (the command's stderr says so); with none of them, `--local` exits 1 and the default in-session mode still works. `provider: none` disables the reasoner like everything else. `BRAIN_REASONER=<model>` overrides the model for one run.

| Key | Default | Meaning |
|---|---|---|
| `reasoner.model` | `claude-opus-5` | The Claude model id (or alias) the reasoner runs on. |
| `reasoner.perCallUsd` | `0.5` | `--max-budget-usd` for one reasoner call. |
| `reasoner.perDayUsd` | `5.0` | Daily cap over `reason:*` ledger rows; at the cap the reasoner resolves to `none` (`reasoner-daily-cap`) until local midnight. |
| `reasoner.effort` | `medium` | `--effort` for the call: `low`, `medium` or `high`. |

**The Codex provider.** `codex.model` (default `null`: no `-m` is passed, so Codex uses the model its own config selects), `codex.effort` (default `low`: background calls never inherit a slow, expensive reasoning default from your Codex config; a caller that asks for more still gets it), `codex.perCallUsd` (`0.05`, an estimate ceiling — Codex has no budget flag) and `codex.perDayUsd` (`0.5`, over the same hook ledger). `AOS_CODEX_MODEL` overrides the model for one run. Structured calls (memory extraction, correction drafts, conflict checks) pass their JSON Schema in the strict form `codex exec --output-schema` requires; a free-form JSON request is asked for in words. File maps and workspace insights use the model under Codex only when you opt in (`scan.fileMapBudgetUnderCodex`, `scan.insightsUnderCodex`, off by default), like their Claude twins. Rates live in `brain/scripts/sdk/lib/codex-pricing.js` and are estimates to verify against the published price list.

**Ollama endpoint.** `ollama.host` / `ollama.port` in `agenticos.json` (or `brain/config.json`) outrank the `OLLAMA_HOST` / `OLLAMA_PORT` environment variables for every provider-routed call and for the `aos doctor` / `aos init` probe; the environment variables apply only when those keys are absent.

**What the Claude provider spends.** Under `claude`, a session end costs two to four Haiku calls (working-memory summary, memory extraction, correction check, scan insights when enabled) plus one call every ~5 turns for the summary — roughly a cent or two per session at the measured ~$0.0034 per call. When the day's hook spend reaches `claude.perDayUsd` (default 0.50) the provider resolves to `none` with reason `daily-cap` until local midnight: summaries fall back to heuristics and the pipeline ledger shows those stages gray (`skipped` / `disabled`), never red. `aos status` shows the running totals (hooks, duties, reasoner, routines, graph, cross-review, teams), each cap, the reasoner model, the resolved `claude` binary and the cached login state; `aos provider <mode>` clears that cache. Chat rows from the Workbench's Chat tab are reasoner calls (feature `reason:chat`) and count toward `reasoner.perDayUsd`; each cap is enforced the next time its provider resolves — the next hook run (a Stop or SessionEnd hook, or `aos scan-vault --quiet`) for the hook cap, the next reasoner command for the reasoner cap.

**In-session commands.** `/ask-brain`, `/standup`, `/reflect-week`, `/consolidate-memory` and `/compress` print an assembled context block by default and let Claude answer in your own session; that step persists nothing model-generated. The one write it may perform is recall's self-heal: a missing `brain/_index/recall-index.json` is rebuilt in pure Node, with no model call.

**The vault graph's semantic pass.** At most every `graph.semantic.everyHours` (24) a scan starts `graphify extract <vault> --backend claude-cli` in the background. graphify's model calls go through a `claude` shim (`brain/scripts/bin/graph-shim/claude` → `graph-claude.js`) that runs your `claude` CLI exactly like the other headless calls — no tools, none of your settings, hooks or `CLAUDE.md`, no MCP servers, `AOS_HEADLESS=1`, `MAX_THINKING_TOKENS=0`, `--model <claude.model>`, `--max-budget-usd <graph.semantic.perCallUsd>` — and ledgers each call as a `graph:semantic` row. Where Codex is the host the same shim answers through `codex exec` instead (`sdk/lib/codex-cli.js`: read-only, ephemeral, our hooks off, in an empty folder, `codex.model` at low effort) and prints the result envelope graphify reads; Codex has no per-call budget flag, so `perCallUsd` does not apply and each call's spend is estimated from its token counts (measured: about 20 k input tokens of Codex's own context per call, most of it cached on the calls that follow). `graph.semantic.runner` picks the CLI: `auto` (an explicit `provider: claude` or `codex` names it, else Claude when it is a host, else Codex), `claude` or `codex`. Those rows have their own cap, `graph.semantic.perDayUsd` (1.0), and never count against `claude.perDayUsd`; once it is reached the shim refuses further calls and the remaining notes wait for the next run. `graph.semantic.enabled` is `"auto"` (on unless the provider is explicitly `ollama` or `none`), `true` or `false`.

**Routines.** A `kind: prompt` routine (`brain/routines/<slug>.md`) runs headless Claude under its own caps: `routines.perRunUsd` per run (`budgetUsd:` in the file overrides it) and `routines.perDayUsd` per day, summed over the `routine:*` ledger rows; a capped day skips the run and records why in `brain/_index/routines.json`. `routines.tools` is the `--allowedTools` list those runs get (default `Read,Glob,Grep`). Duties keep the `persona.*` caps and `command` routines spend nothing. `routines.externalLabels` lists launchd labels the HUD's Routines tab shows read-only under "Outside the runtime". `aos upgrade` seeds `brain/routines/` once on a vault that predates routines and re-renders any installed schedule from the routine files.

## Update checks

### `updates`

| Key | Default | Meaning |
|---|---|---|
| `updates.check` | `true` | Whether to check GitHub Releases for a newer version. |
| `updates.intervalHours` | `24` | Minimum hours between checks. Doubles on consecutive failures, capped at four doublings. |

Set in `brain/config.json`, or in `~/.claude/agenticos.json` to override it (`agenticos.json` wins).
`aos update-status --off` writes `updates.check = false` to `agenticos.json`. The check is
unauthenticated and sends nothing but an HTTP GET to `api.github.com`.

## Uninstall

`aos uninstall --keep-vault` leaves `~/.claude` as it was and keeps the vault. No form of `aos uninstall` (`--keep-vault`, the full one or `--host claude`) edits your `CLAUDE.md`: remove the `@<vault>/AGENTICOS.md` line yourself from `~/.claude/CLAUDE.md` (or `$CLAUDE_CONFIG_DIR/CLAUDE.md`). You added it from the installer's checklist, or the app's wizard added it at your request. `aos uninstall` additionally deletes the vault after you type its path (or with `AOS_CONFIRM_DELETE=<vault>` for scripts). `--yes` skips the prompt and always keeps the vault; deletion needs the typed path or `AOS_CONFIRM_DELETE=<vault>`.

## Rehearsing an install without touching your machine

`sh cli/rehearsal/first-run.sh` does the whole first run in a temporary HOME and config dir with a fake `claude`, then checks recall and `wrap_session` over MCP and uninstalls. `sh cli/rehearsal/codex-host.sh` does the same for a Codex-only machine with a fake `codex`: it installs the direct wiring on a CLI without plugins and runs its hook commands for real (the conventions injection, the Stop hook's `{}`, the first-prompt context), then upgrades to the Codex plugin, checks that the direct wiring is gone, runs the plugin's own hook commands the way Codex runs them and completes an MCP handshake from the plugin folder, then doctor and uninstall. CI runs both on Ubuntu and macOS.
