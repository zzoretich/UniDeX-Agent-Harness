# UniDeX Browser: one per session, switched by the user, usable by any model — design

**Date:** 2026-11-11
**Status:** draft, awaiting the owner's approval. *(user)* rows are the owner's interview answers; *call* marks a decision made for the owner to check; the rest are proposed technical decisions. A builder check on 2026-11-11 returned ten questions; all are settled here (S1, S5, S7, S14–S17, S21, S22). S23 and S24 were added at the owner's request after that check and have not been through one. Mockups are private (a local brainstorm: pane sizes, five power moments).
**Base:** `main` at `fe8e19a` (2.6.0 plus #197). Follows `2026-11-06-agent-computer-design.md`, whose decisions are cited as AC-D<n> and whose build rulings as R<n>. This design **supersedes AC-D3, AC-D30, AC-D32 and the shared tabs of AC-D31**; everything else there stands: the gate (AC-D6, D7, D39, D43), admission (AC-D18), one profile (AC-D9), off-screen work (AC-D27), and Your Mac (AC-D14, D15), which is unbuilt and untouched. Code comments cite `session-browser S<n>`.
**Scope:** the Computer pane's browser becomes one browser per session that starts off and that only the user switches on or off; the pane becomes resizable in practice and navigable; links clicked in a session, and pages a session's programs open (Superpowers' visual companion, a dev server, a sign-in page), open in it; and the agent's side (a skill, server instructions, four more tools, replies that carry the page, a visible pointer) is built so that a model with no tools of its own could drive it.

---

## 1. Problem (verified at fe8e19a)

1. **Sessions do not use the browser.** Nothing introduces it: the agenticos MCP server sends no instructions (`brain/scripts/sdk/mcp-server.js:37`), no skill covers it, and `AGENTICOS.md` cannot carry it (the template is at its 9,000-character limit and an upgrade never rewrites a vault's copy). A host that loads tools by search finds one of the nine with the words "browser open web page": the other eight are named `computer_*` and described as "the Computer pane".
2. **One browser per folder.** Every session in a workspace, or in the vault, shares one set of tabs and one wheel (`app/src/main/computer/service.ts:240`); the vault is where agents start by default, so most sessions share one browser and a second one is told "busy".
3. **No off.** A browser is made on first use and destroyed only at quit (`app/src/main/index.ts:453`); its tabs are gone after a restart.
4. **The pane is too small to work in.** 320–900 px, 440 by default (`hud/src/settingsDefaults.ts:319`), behind a 6 px grab strip drawn only on hover (`hud/styles.css:5564`); it has no Back, Forward or Reload.
5. **localhost opens nowhere.** A link clicked in a session is handed to `shell.openExternal` (`hud/src/ui/TerminalPanel.ts:677`), and main lets only `https:` out to the default browser (`app/src/main/policy/shell.ts:29`). An `http://localhost` link is dropped, so a session's own dev server cannot be opened from the app at all; every other link, and every page a program in the session opens (a sign-in, Superpowers' visual companion), lands in the default browser, where the session cannot see it.
6. **The tools assume a strong model.** An action replies one line (`service.ts:365`), so the model must look again to see the result; there is no way to switch or close a tab, go back or read a page's console; and nothing shows the user where the agent is acting.

## 4. Design

### 4.1 Keys, states and records (main)
`ComputerService` is keyed by session key; an agent's `place` remains only as a label. `policy/computer.ts` admits a key the page names when it is `code:<id>` for a terminal the PTY service holds, or `chat:<thread>` for a thread file in the vault's index. A browser is **off**, **on and awake** or **on and asleep**. `computer/records.ts` (new, no Electron) keeps `<user data>/computer/browsers.json`, written atomically at mode 0600: per key `{ on, tabs, active, conversation?, at }`. Tab addresses are stored as they are, as the profile's own history is, and never leave main unscrubbed (S9). A thread's record keeps its key across runs. A Code record is under `code:<id>` only while the page that made the terminal lives: `move` re-keys it (S7a), and when the page goes or the app starts it becomes an orphan under its host and conversation id (S7b). Close session and Delete thread forget a key; nothing else does.

### 4.2 Power
The page's `power(session, on)` and the `power` ask (S3) are the only ways on; Off (S5) destroys the views, cancels the session's asks and bumps the wheel's generation. A thread's turn ending never changes power.

### 4.3 The pane (HUD)
`ComputerPane.follow({ session, label })` replaces the place; `computerStore` is keyed by session, and a row's dot is its own browser's. The strip, the header switch and the size buttons are S11 and S12. `TerminalPanel.openLink`, the Code chat's `openLink` and the thread reader send an `http:` or `https:` link to `openLink(session, url)` when the link is in a session, and everything else where it goes today.

### 4.4 Tools and replies (runtime and main)
`computer-tools.js` gains the four tools and `double`, and every description is rewritten for S15 and S16d; its two pinned copies, `headless.js` and the Codex approval tables follow, so Codex users get the new acting tools approved by `aos upgrade` (an **Upgrading** line). In `service.ts` every acting call's reply is built by one function that appends the outline (S16b), and every refusal comes from one table of sentences (S16c). `computer_console` turns on the Runtime and Network protocol events for a tab while it is awake and keeps the last 200 entries per tab.

### 4.5 The pointer (main)
`computer/pointer.ts` owns one `ImageView` per window that shows a browser (the main window and the pop-out), placed above the active tab's view and moved by `setBounds`. Its image's tip is its top-left corner, so it covers nothing clickable beyond its own drawing.

### 4.6 The skill and the instructions (plugin and runtime)
`plugin/skills/browser/SKILL.md`, host-neutral, generated into `codex-plugin/`: when to use it, the loop (status, open, read, act, wait on an ask), and the rules of S3, S4, AC-D6 and AC-D21. The server's `instructions` say in under 600 characters that a UniDeX session has its own browser through the `computer_*` tools. The counts become 10 skills and 29 Codex skills.

### 4.7 The page's calls
`window.aos.computer.select` takes a session key, and six calls are added: `power`, `nav`, `openLink`, `describe` (S22), `move` (S7a) and `openOutside` (S24: no argument, the selected browser's active tab, sent by main with its real address); `window.aos.sessions` gains `remove`. Each is a channel with its schema, its rule in `app/src/main/policy/`, its line in `sandbox.spec.ts` and a line in `SECURITY.md`; `remove` is a write the `sessions` surface must list.

### 4.8 The opener (app)
One executable Node script shipped in the app (a `.js` file with a shebang, so it serves tools that execute `BROWSER` and tools that run a `.js` browser with Node). `computer/door.ts` (new) listens on a second Unix socket at mode 0600 beside the bridge's, holds each live session's id, checks that the address is `http:` or `https:` (the schemes AC-§4.2 lets the browser open) and applies S23's limit. The opener sends anything else to the `BROWSER` the session's environment had before the app set its own, else to the system's `open`. The id leaves main only in that session's environment, in one variable whose name avoids the words a host's shell filter drops. `pty.ts` and `sessions.ts` add the three variables where they build a session's environment.

## 5. Host parity

1. **Entry point:** the pane is host-neutral. Claude Code: the `agenticos:browser` skill and `mcp__plugin_agenticos_agenticos__computer_*`. Codex: `$agenticos:browser` (direct wiring `$browser`) and `mcp__agenticos__computer_*`.
2. **Hooks:** none added or changed.
3. **Model calls:** none; outlines and screenshots are tool results inside the session's own turns.
4. **Session data:** no transcript reads. A Code terminal's conversation id comes from the HUD's existing model of the runtime's caches, on both hosts (S7b, S22).
5. **MCP:** four new tools in the existing server, one name per host; the skill's source names the Claude form and the generator rewrites it. Claude sessions pre-approve them at launch; Codex in plugin and direct mode after `aos upgrade`, which the app offers after an update.
6. **Degradation:** a session outside the app, an unadmitted process, a Read only session, an off browser and a declined power ask each get one sentence that names the next step (S16c). A Codex session that has not had `aos upgrade` is asked by Codex for the four new tools (Code) or refused them (Chat) until it has; the nine it had still work. If a host does not show a server's `instructions`, S16d and the skill still carry the guidance. A program that honours neither of S23's variables opens the default browser as it does today, and the skill has the agent open its address with `computer_open`.

## 7. Out of scope

Your Mac (AC release 2), unchanged. A session type for a local model and its admission (AC-D18 admits only a Claude Code or Codex CLI the app started): this design only avoids blocking one. A program that opens a page by running the `open` command directly and honours neither `BROWSER` nor `BRAINSTORM_OPEN_CMD`: catching it means shadowing a system command on `PATH`, which a login shell's `path_helper` reorders anyway. A profile per session. Scripts in pages, uploads by the agent, drag and drop, context menus. A browser of the user's own for links clicked outside a session (Notifications, Vault chat, a past conversation): they go where they go today. Background duties and Vault chat. Renaming the Computer pane in the app. Linux and Intel Macs.
